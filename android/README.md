# SAFE_Links — Android app

One app for everyone — resellers, Super Admin, and field technicians pairing
routers. It's a thin native wrapper (Capacitor WebView) around the whole
SAFE_Links web app.

**A small native picker runs once, on first launch**, before anything web
loads: "I'm a Reseller / Admin" or "I'm pairing a router". This isn't
decorative — it's the only way `/install` is reachable at all from inside
this app. An earlier version of this README claimed the web app's welcome
screen has "a link right on it" to `/install`; that turned out to be false
— checked directly against `frontend/src/App.jsx`'s `Landing` component,
and that text (`Installing a router? Go straight to /install...`) is
plain, non-clickable text, meant for a browser user who can type a URL.
A Capacitor WebView has no address bar, so without a native picker, a
field technician handed this app would have no way to reach the pairing
wizard at all.

Once past the picker, routing works exactly like the website:

- **Not signed in** (Reseller/Admin mode) → the welcome screen (Create
  account / Log in / Super Admin)
- **Signed in as a reseller** → straight to the Reseller dashboard
- **Signed in as Super Admin** → straight to the Super Admin dashboard
- **Installer mode** → the router-pairing wizard directly, no login screen
  first

The picker's choice, and your login session, are both remembered across
app restarts — this genuinely behaves like "one app, routes you to your
own thing" rather than re-asking every time you reopen it. A small
"Switch mode" button floats over the top-right corner of every screen if
you ever need to go back and pick differently (that's a real button, not
a hidden menu — see the note on why, below).

This is a real, complete Android Studio project — not a scaffold you need
to finish assembling. It opens and builds as-is. The one thing you must do
first is point it at your live server (see below).

## 1. Point it at your server

Right now the app is configured to load:

```
https://REPLACE-WITH-YOUR-DOMAIN.com/
```

Once you've deployed the SAFE_Links frontend + backend (see the `deploy/`
folder and root `README.md` in the main SAFE_Links zip — Docker Compose +
Caddy handles this in one command), edit **`capacitor.config.json`** in
this project's root and replace that URL with your real domain, e.g.:

```json
"server": {
  "url": "https://portal.yourcompany.com/",
  "cleartext": false
}
```

Then re-sync it into the native project:

```bash
npm install
npx cap sync android
```

(`cleartext: false` means HTTP-only URLs won't load — intentional, this
app should only ever talk to your server over HTTPS. If you're pointing
this at a plain-HTTP staging server to test first, temporarily set it to
`true`, but don't ship that.)

## 2. Open in Android Studio

- Android Studio (recent version) with the Android SDK installed —
  Studio will prompt to install anything missing (SDK platform 36,
  build tools) the first time you open this project.
- `File → Open` → select the `android/` folder in this project (not
  the project root — `android/` is the actual Gradle project).
- Let Gradle sync finish (first sync downloads dependencies, can take
  a few minutes).

## 3. Run it / build a debug APK

- Press ▶ Run in Android Studio with a device or emulator connected —
  this installs a debug build directly, good enough for testing on
  your own phone.
- Or from the command line: `cd android && ./gradlew assembleDebug` —
  output lands at `android/app/build/outputs/apk/debug/app-debug.apk`.

## 4. Build a signed release build (for real distribution)

A debug APK is NOT what you distribute — it's unsigned (well, signed
with a throwaway debug key) and not optimized. For that you need your
own signing key, which I deliberately have NOT generated for you — a
release keystore is a secret you must generate and keep yourself; anyone
with it can publish updates to your app under your identity, so it
should never be generated by a third party or committed to version
control.

**Generate your own keystore once** (keep the resulting `.jks` file and
its passwords somewhere safe — losing it means you can never update this
app again under the same identity):

```bash
keytool -genkeypair -v -keystore safelinks-release.jks \
  -alias safelinks -keyalg RSA -keysize 2048 -validity 10000
```

**Then in Android Studio:** `Build → Generate Signed Bundle / APK` →
choose *Android App Bundle* (`.aab`, what Play Store wants) or *APK*
(if distributing directly) → point it at your `.jks` file → build the
`release` variant.

## What's already configured

- **App ID**: `com.aibrainsventures.safelinks`
- **App name**: SAFE_Links
- **Min SDK**: 24 (Android 7.0+) — **Target/Compile SDK**: 36 (current)
- **Icon + splash screen**: generated from the SAFE_Links brand colors
  (`#667eea` → `#764ba2`), already placed at every density Android
  needs. To replace with real artwork later: drop new `icon.png`
  (1024×1024) and `splash.png` (2732×2732) into `assets/`, then
  `npx capacitor-assets generate --android` regenerates everything.
- **Permissions**: `INTERNET`, `RECORD_AUDIO`, `MODIFY_AUDIO_SETTINGS`
  (voice-note recorder on support tickets), `ACCESS_NETWORK_STATE` +
  `ACCESS_WIFI_STATE` (LAN router auto-pairing — see below; neither
  grants SSID/location access, just "is there a network, is it WiFi").
- **Offline fallback page** (`www/index.html`): shown only if the app
  can't reach your server (no connection, or the URL above hasn't been
  set yet). It is NOT the app itself — every screen (dashboards,
  installer wizard, everything) is always loaded live from your
  server, never bundled into the app. This means every update you make
  on your server is automatically live in this app too, with no
  app-store update needed.

### Native fixes beyond the default Capacitor scaffold

A plain `npx cap add android` gets you a WebView that can load your site,
but a few things the real app actually *does* — attach a receipt photo,
record a voice note on a support ticket, open a "view receipt" link, use
the back button mid-flow — don't work out of the box in a stock WebView.
These are fixed in `MainActivity.java` / `ExternalLinkWebChromeClient.java`,
each with a comment explaining why:

- **"View receipt" / "view attachment" links** (`target="_blank"`) —
  a stock WebView does nothing at all with these. Fixed by enabling
  `setSupportMultipleWindows` and handling `onCreateWindow` to open the
  link in the device's own browser/PDF/image viewer instead.
- **Voice notes on support tickets** — needs the `RECORD_AUDIO` /
  `MODIFY_AUDIO_SETTINGS` permissions declared (added to the manifest);
  Capacitor's own bridge already handles the runtime permission prompt
  once they're declared, no extra code needed for that part.
- **Attaching a receipt photo/file** — this one needed nothing extra;
  Capacitor's default `BridgeWebChromeClient` already implements a full
  native file picker for `<input type="file">`. Confirmed by reading
  Capacitor's own source rather than assumed.
- **Hardware/gesture back button** — Capacitor's `BridgeActivity` does
  not handle this at all by default, which means back would exit the
  whole app immediately from anywhere, including mid-way through the
  Captive Portal's plan → pay → confirm flow. Fixed to navigate the
  WebView's own history first, only exiting once there's nothing left
  to go back to.
- **Keyboard covering input fields** — `android:windowSoftInputMode="adjustResize"`
  added, since this app is form-heavy (login, signup, payment forms).
- **`/install` unreachable from a cold launch** — see above. Fixed with
  `PickerActivity` (now the actual launcher activity) plus a small
  floating button `MainActivity` adds on top of the WebView at runtime.
  That button — not a standard Options Menu — is deliberate:
  `MainActivity` runs under `AppTheme.NoActionBarLaunch` (parent
  `Theme.SplashScreen`) for its *entire* lifetime, not just during the
  splash screen, so there's no ActionBar/Toolbar to host an overflow
  menu button. One would compile fine and simply never be reachable by
  any visible UI on a modern phone — confirmed by reading `styles.xml`
  and the manifest together, not assumed.

### LAN router auto-pairing (new)

Pairs a MikroTik router directly over the local network instead of
someone typing the pairing code into the router's console by hand — if
the phone's on the same WiFi as the router. Exposed to the web app as
`Capacitor.Plugins.RouterLanPairing` (`RouterLanPairingPlugin.java`,
`RouterOsClient.java`, `RouterOsScripts.java`, `GatewayLocator.java`),
wired into the pairing UI via `frontend/src/InstallerWizard.jsx`'s
`LanAutoPair` component (see that file — the integration is already
applied, not left as a manual patch).

This is a genuinely different trust model from the rest of the app, so
it's worth reading in full before turning it on for real users:

- **Trust-on-first-use certificate pinning, not blind trust.** RouterOS's
  REST API ships with a self-signed cert by default. The first
  connection in a pairing session captures its SHA-256 fingerprint and
  shows it on-screen for a human to compare against the router's own
  sticker/console before anything changes; every connection after that,
  within the same session, must present that exact fingerprint or the
  request fails closed (`RouterOsClient`'s `CertMismatch` result).
- **Requires the router's admin password, typed in fresh each time.**
  Never stored, never defaulted to blank/factory credentials — that
  would turn "anyone on this WiFi" into "anyone on this WiFi can
  reconfigure this router."
- **Only helps MikroTik routers with the REST API (`www-ssl`) enabled.**
  Everything else still needs the manual/human-typed pairing flow —
  `LanAutoPair` simply doesn't render its automatic option if the
  Capacitor plugin isn't available (e.g. running in a browser instead
  of this app).
- **The generated RouterOS script faithfully ports the logic of its
  source, but isn't a byte-identical copy.** `RouterOsScripts.java`
  reproduces the same HTTP calls, response parsing, and hotspot-user
  command handling as
  `reslink-backend/router-scripts/reslink-agent.rsc` — verified by
  actually diffing a Node.js port of the same logic against that file
  directly (this file itself couldn't be verified that way — no JVM
  in the environment this was built in). It deliberately restructures
  the one-shot registration step to run inline via `/rest/execute`
  instead of as a separate persisted script object, and log message
  wording is paraphrased rather than copied verbatim — neither changes
  what the router actually does. That source file's own header says it was written
  against documented RouterOS 7 syntax, not validated against physical
  hardware. Test against a spare device or a Cloud Hosted Router before
  relying on this with a paying reseller's install.
- **Assumes frontend and backend share an origin** — `apiBaseUrl` for
  the RouterOS script is derived from `getBridge().getServerUrl()`
  (this app's own configured URL), not a separate setting. True by
  default in this project's `docker-compose.yml`/Caddy setup; if that
  ever changes, this needs its own config field instead.

I don't have the Android SDK in the environment I built this in, so I
couldn't run an actual Gradle build to prove these compile — what I did
do: read Capacitor's own library source directly to confirm every method
and field this code touches genuinely exists and is accessible (not
guessed from memory — this is how `RouterLanPairingPlugin.getBridge().getServerUrl()`
got verified, for instance), checked every `R.id`/`R.string`/`R.layout`
reference in the new Java files against what's actually declared in
`res/`, hand-verified brace/parenthesis balance across every new file,
and confirmed both `AndroidManifest.xml` permissions
(`ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`) that `GatewayLocator`
needs are actually present — an earlier pass had missed
`ACCESS_NETWORK_STATE` entirely, which would have crashed LAN pairing
with a `SecurityException` at runtime rather than a compile error, so
that one's worth knowing was a real gap that got caught, not a
hypothetical. First Gradle sync in Android Studio is still the real
confirmation — if anything's off, it'll surface there immediately and
clearly.

## One app, not three

There's deliberately no separate "installer" build anymore — the
earlier version of this project was scoped to just the router-pairing
wizard. That's now folded into this single app, since the real website
already handles routing people to the right place based on who's
signed in. Simpler to distribute (one APK/Play Store listing instead of
several) and one less thing to keep in sync.
